## What was actually checked, and how

Everything below was either read in the source with a line to point at, measured against the
live database with a read-only query, or reproduced in a real browser. Where something could
not be established that way it says so rather than guessing.

* **Routes and permissions** — all 162 HTTP routes were extracted with their `onRequest` /
  `preHandler` guards, including the module-level `addHook` guards, because most admin
  modules are gated once for the whole plugin rather than route by route.
* **The database** — read-only `SELECT`s against the production instance: row counts,
  orphans, duplicates, foreign-key actions, `pg_stat_user_tables`, and `EXPLAIN ANALYZE` on
  the one query this report calls slow. Nothing was written and nothing was deleted.
* **The client** — booted in headless Chromium against the live site and against a
  throwaway instance built from this commit, signed out and signed in, every route, at
  1280 px and at 430 / 390 / 375 px.
* **The build** — `docker build` from this commit, `npm ci`, the full web test suite, and
  `standard` over the client.

### What came back clean

Worth saying, because a report that lists only problems misrepresents the codebase:

* **No admin endpoint is gated in the client only.** Of 162 routes, 25 are unauthenticated,
  and all 25 are public by design: the catalogue reads, `robots.txt` / `sitemap.xml` /
  `/anime/:id`, the health probe, the changelog, and the four auth endpoints. Every
  administration route carries `requirePermission(..., { hide: true })`.
* **`require_login` is enforced on the server.** A private instance answers
  `/v1/anime/search` with 401 to an anonymous caller, not just with a client-side gate.
* **No IDOR found.** The `X-Profile-Id` header — the one obvious candidate, since the client
  sends it on every library call — is checked against `user_profiles.user_id` in both the
  REST path and the GraphQL context. Room deletion, topic edits and library writes are all
  scoped to the caller in the statement itself.
* **SSRF is handled.** `checkOutboundUrl` resolves DNS and refuses private, loopback,
  link-local and IPv4-mapped ranges, and it is called at all three places that fetch a URL a
  person supplied.
* **Validation is nearly complete.** Exactly two write routes read a body without a JSON
  schema, and both coerce safely (YUME-AUDIT-0019).
* **Invalid input is handled.** A malformed UUID gives 400 with the reason, an unknown one
  404, an over-long path 404. No 500s.
* **Foreign keys are complete.** 157 of them, every one with an explicit `ON DELETE`
  (129 CASCADE, 28 SET NULL). Every table has a primary key. No orphaned episodes, no
  orphaned titles, no duplicate `(anime_id, number)` episode pairs.
* **No horizontal overflow at any of the three mobile widths**, on any route, signed in or
  out — measured element by element, excluding containers that are meant to scroll.
* **No broken internal links.** Every `#/…` href in the client resolves to a route or a
  redirect in `router.js`.
* **No dead controls found.** Every button, toggle and select that a static scan flagged
  turned out to be wired — the scan's misses, not the code's.

### Two things this audit could not establish

* **Whether the 1 335 reachable-but-empty synopses are upstream gaps or failed writes**
  (YUME-AUDIT-0010). Not checkable statically: `metadata_runs` records counts, not per-row
  outcomes, so "AniList has no description" and "never attempted" look identical from here.
* **Whether `anime_relations`' 421 084 sequential scans are a missing index or the planner
  being right** (YUME-AUDIT-0021). Not checkable statically: it needs `EXPLAIN` against the
  real query on the real distribution, and the query varies by call site.

## CRITICAL

### YUME-AUDIT-0001 — The pre-namespace key migration needed room for the library twice

* **File:** `apps/web/src/shared/state/store.js:120` (`Store._renameKey`, previously inline in
  `ensureProfiles`)
* **Effort:** S · **Status: fixed in this change**

**What was wrong.** `ensureProfiles()` moved three pre-namespace localStorage keys to their
`::<viewer-id>` spelling by writing the new key and then deleting the old one. For the
moment between those two statements the value existed twice. The founder's library is the
whole catalogue, and the store already knows that does not fit in the quota once — see the
trimming logic in `saveEntries`. So `localStorage.setItem` threw `QuotaExceededError`.

**What it did to the viewer.** `ensureProfiles()` is the first statement of `App.init()`. The
exception propagated out of it, the router never ran, and `<main id="page">` stayed empty:
a blank page. Every symptom pointed away from the cause — `/` returned 200 with the right
HTML, every module returned 200 with the right content type, `/v1/health` was fine, and the
server log was clean, because nothing had gone wrong on the server.

**Reproduced**, before and after, in headless Chromium against an instance built from this
commit: seed a pre-namespace `animelist` of 6 000 entries, load the page. Before:
`QuotaExceededError`, `#page` has 0 children, no text on the page at all. After: the page
renders, the bare key is gone, the namespaced key holds all 6 000 entries, and storage holds
one copy rather than two.

**The fix.** Free the old value first, then write the new one, so the rename needs no more
room than the value already occupies; if it still fails, put the value back exactly where it
was and let the application start. A rename that does not happen costs the viewer nothing;
an application that does not start costs them everything.

`apps/web/test/store-migration.test.mjs` covers it, against a fake `Storage` that has a real
quota — a test against an unbounded `Map` cannot tell the two spellings apart. It fails on
the old code and passes on the new.

## HIGH

### YUME-AUDIT-0002 — 11 703 anime carry no `anilist_id`, so the enricher can never match them

* **File:** `apps/api/src/integrations/anilist/sync.ts:187`
* **Effort:** M · Status: open

This supersedes the hypothesis this audit was asked to check. The `anime_mappings_mal_id_key`
collision **is already fixed**: migration `0026_mapping_conflicts.sql` and `writeMalId()`
replaced the blind `UPDATE` with a guarded one that cannot raise, and the collisions are
recorded instead of taking their batch down. 368 conflicts are on record where a run used to
lose 9 650 rows.

What the live database says now:

| | rows |
| --- | ---: |
| anime | 32 390 |
| with a synopsis | 19 352 |
| **without a synopsis** | **13 038** |
| — of those, with an `anilist_id` | 1 335 |
| — of those, **without** an `anilist_id` | **11 703** |
| mappings holding `mal_id` but no `anilist_id` | 11 703 |

`upsertMedia()` finds its row with `SELECT anime_id FROM anime_mappings WHERE anilist_id = $1`
and returns `false` when there is none. Those 11 703 rows came from a MAL-keyed dump and hold
a `mal_id` only, so the enricher has never been able to see them and never will. That is 36%
of the catalogue, and it accounts for 90% of the missing descriptions — the collision bug
accounts for none of them any more.

**Fix in one sentence:** give the enricher a MAL-keyed path — resolve `anilist_id` from
`mal_id` once via AniList and store it — so a row seeded without an AniList id becomes
reachable.

### YUME-AUDIT-0003 — The SPA fallback answers a missing client module with `index.html` and a 200

* **File:** `apps/api/src/app.ts:422`
* **Effort:** S · Status: open

`setNotFoundHandler` returns `index.html` for any non-API GET, which is right for
`#/anything` and wrong for `/src/pages/whatever.js`. A module that stops resolving — moved by
a restructure, mistyped in a path — is served as HTML with a 200. The browser refuses to
execute it, the page goes blank, and every check an operator makes reports health: the JS URL
returns 200, and the server logs nothing because nothing failed.

Verified against the live site: `/src/does-not-exist.js` → `200 text/html`.

No module is currently missing — all 42 resolve, and all 42 are served as
`application/javascript`. This is about the next one.

**Fix in one sentence:** exclude the client asset directories from the SPA fallback so a
missing file under `/src`, `/css` or `/assets` returns a real 404.

### YUME-AUDIT-0004 — `POST /v1/anime/resolve` lets any account create catalogue rows at the global rate

* **File:** `apps/api/src/modules/catalogue/public-routes.ts:347`
* **Effort:** S · Status: open

The route is authenticated and validated, and then it calls `animeRepo.createStub()` for any
AniList id it has not seen. Its only limit is the global 300 requests a minute; `WRITE_LIMIT`
is not applied and there is no per-account cap. One ordinary account can insert hundreds of
thousands of rows a day into `anime` — the table this instance most needs to protect — and
each one appears in search and in the sitemap.

**Fix in one sentence:** apply `WRITE_LIMIT` and cap how many stubs one account may create
per day.

### YUME-AUDIT-0005 — `docker build -t yume-test .` fails

* **File:** `infrastructure/docker/Dockerfile:8`
* **Effort:** S · Status: open

```
$ docker build -t yume-test .
ERROR: failed to solve: failed to read dockerfile:
       open Dockerfile: no such file or directory
```

The restructure that created `infrastructure/` moved the Dockerfile and left nothing at the
root. `.github/workflows/check.yml:219` names the file explicitly, so CI is green and cannot
warn anybody — but the habitual command, the one somebody reaches for while shipping a fix in
a hurry, is broken.

With the file named, the build passes from this commit:
`docker build -f infrastructure/docker/Dockerfile -t yume-test .` → exit 0.

**Fix in one sentence:** either restore a root Dockerfile or correct every runbook to the
`-f` form, and say which one is canonical.

## MEDIUM

### YUME-AUDIT-0006 — Tokens live in localStorage, where script can read them

* **File:** `apps/web/src/shared/api/yume.js:36` · **Effort:** L · Status: open

The audit asked about `HttpOnly`, `Secure` and `SameSite`. There is no cookie anywhere in the
API, so those flags are not unset — they are unavailable. Both tokens sit in localStorage, and
the refresh token is good for 30 days. `script-src 'self'` is the only thing in front of them,
which makes a single injection into a same-origin file a full account takeover rather than a
session-long nuisance.

**Fix in one sentence:** move the refresh token into an `HttpOnly; Secure; SameSite=Strict`
cookie and keep only the short-lived access token in memory.

### YUME-AUDIT-0007 — The donut legend interpolates its label into `innerHTML`

* **File:** `apps/web/src/shared/ui/charts.js:242` · **Effort:** S · Status: open

`row.innerHTML = \`…${d.label}…\`` with no escaping. Today the labels are genre and format
names, so reaching it needs `anime.edit` — but it is an unescaped HTML sink on a page an
administrator opens, which makes it a step up rather than a dead end, and nothing stops a
future caller passing a username.

**Fix in one sentence:** build the row from elements and `textContent`.

### YUME-AUDIT-0008 — The metric-age probe sequentially scans every `system_metrics` partition

* **File:** `apps/api/src/modules/system/diagnostics.ts:256` · **Effort:** S · Status: open

`SELECT max(created_at) FROM system_metrics` has no index it can use — the only one is
`(metric, created_at DESC)`. Measured on the live database:

```
Parallel Seq Scan on system_metrics_2026_09  (rows=77315 loops=3)
Buffers: shared hit=2689        Execution Time: 28.037 ms
```

`pg_stat_user_tables` records 34 198 sequential scans of that partition. The cost grows with
the retention window.

**Fix in one sentence:** index `created_at`, or take the age from `system_metrics_hourly`,
which is small and already ordered.

### YUME-AUDIT-0009 — 343 unresolved mapping conflicts are shown nowhere

* **File:** `database/migrations/0026_mapping_conflicts.sql:24` · **Effort:** M · Status: open

The recording half of 0026 works: 368 rows, 343 unresolved. The reviewing half does not
exist — no route reads `mapping_conflicts`, no screen shows it. The table's own comment calls
it a review queue and there is no queue, so the candidate duplicate pairs it was built to
surface sit where nobody looks. `resolved_at` has never been set.

**Fix in one sentence:** add a read route and a catalogue-section list for unresolved
conflicts, with the resolve action the column was added for.

### YUME-AUDIT-0010 — 1 335 anime have an AniList id and still no synopsis

* **File:** `apps/api/src/integrations/anilist/sync.ts:196` · **Effort:** M · Status: open

**Not checkable statically.** These are the rows the enricher can reach and did not fill.
Whether AniList genuinely has no description, a run has not covered them, or `resolveFields`
refused the write cannot be told apart from outside the process, because `metadata_runs`
records counts and not per-row outcomes. For a viewer it is an anime page with an empty
description and no explanation.

**Fix in one sentence:** record a per-row outcome for each attempt so "nothing upstream" and
"never attempted" stop looking identical.

### YUME-AUDIT-0011 — User-facing write routes with only the global rate limit

* **File:** `apps/api/src/modules/comments/routes.ts:146` · **Effort:** S · Status: open

`WRITE_LIMIT` is applied to eight routes. These are not among them, and 300 a minute is a
flooding budget rather than a limit:

`POST /v1/comments/:id/like` · `PATCH /v1/forum/topics/:id` ·
`PUT` and `DELETE /v1/me/library/:animeId` · `DELETE /v1/me/favorites/:animeId` ·
`PATCH /v1/me/progress/:episodeId` · `PATCH /v1/profiles/me` ·
`PATCH` and `DELETE /v1/me/settings` · `POST` and `DELETE /v1/w2g`

Vote manipulation and write amplification against the database are both cheap at that rate.

**Fix in one sentence:** apply `WRITE_LIMIT` to every mutating route an ordinary account can
reach.

### YUME-AUDIT-0012 — 222 canonical titles are held by more than one anime row

* **File:** `database/migrations/0002_anime.sql:21` · **Effort:** M · Status: open

A duplicate splits a show's episodes, library entries and comments across two ids, and the
viewer sees the same title twice in search with different progress on each. Some are
legitimate — AniList splits seasons MyAnimeList keeps together — which is why they need
looking at rather than assuming.

**Fix in one sentence:** cross-reference the duplicate titles against
`mapping_conflicts.held_by` and merge the pairs that are one show.

### YUME-AUDIT-0013 — `/v1/admin/audit` was already taken

* **File:** `apps/api/src/modules/analytics/routes.ts:232` · **Effort:** S · **Status: fixed**

The audit-status report was specified to live at `GET /v1/admin/audit`. That is the audit
log's route, registered since the admin split. Fastify refuses a duplicate route **at
startup**, so adding the second one would not have failed a request — it would have stopped
the whole application from booting, which is precisely the class of breakage this pass was
told to avoid.

Resolved by giving the two audits distinct names:

| | before | now |
| --- | --- | --- |
| audit log (who changed what) | `GET /v1/admin/audit`, section `audit` | unchanged route, section key **`audit-log`** |
| audit report (this document) | — | `GET /v1/admin/audit/report`, section **`audit`**, page `/admin/audit` |

The only casualty is the deep link `#/admin?s=audit`, which now opens Audit status rather
than the audit log. A bookmark to it lands on a working page, and an account without
`audit.read` falls back to its first available section as it always did.

### YUME-AUDIT-0014 — The palette has no yellow, so two severity levels share the amber hue

* **File:** `apps/web/css/tokens.css:27` · **Effort:** S · Status: open

Severity is meant to read critical red, high orange, medium yellow, low grey. The tokens
offer red, amber and grey and nothing between amber and green. Rather than introduce a colour
for one page, `--severity-high` and `--severity-medium` point at `--amber-500` and
`--amber-400`, so the two differ by lightness within one hue. Severity is never carried by
colour alone — the badge always spells the word — but at badge size the separation is weaker
than the design intends.

**Fix in one sentence:** add a yellow primitive to `tokens.css` and point `--severity-medium`
at it.
