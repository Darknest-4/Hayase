## What was checked, and how

Everything below was either read in the source with a line to point at, measured against the
live database with a read-only query, or reproduced in a real browser. Where something could
not be established that way it says so.

* **Routes and permissions** — all 162 HTTP routes extracted with their `onRequest` /
  `preHandler` guards, including the module-level `addHook` guards, because most admin
  modules are gated once for the whole plugin rather than route by route.
* **The database** — read-only `SELECT`s and `EXPLAIN ANALYZE` against the production
  instance. Nothing was written to it and nothing was deleted; every change was applied and
  tested on a throwaway instance built from this commit, with its own volume.
* **The client** — booted in headless Chromium against the live site and against that
  throwaway instance, signed out and signed in, every route, at 1280 px and at 430 / 390 /
  375 px.
* **The build** — `docker build` from this commit, `npm ci`, both test suites, `tsc --noEmit`
  and `standard`.

### What came back clean

A report that lists only problems misrepresents this codebase:

* **No admin endpoint is gated in the client only.** Of 162 routes, 25 are unauthenticated,
  and all 25 are public by design. Every administration route carries
  `requirePermission(..., { hide: true })`.
* **`require_login` is enforced on the server.** A private instance answers
  `/v1/anime/search` with 401 to an anonymous caller.
* **No IDOR found.** `X-Profile-Id` — the obvious candidate, since the client sends it on
  every library call — is checked against `user_profiles.user_id` in both the REST path and
  the GraphQL context. Room deletion, topic edits and library writes are scoped to the caller
  in the statement itself.
* **SSRF is handled.** `checkOutboundUrl` resolves DNS and refuses private, loopback,
  link-local and IPv4-mapped ranges, and is called at all three places that fetch a
  user-supplied URL.
* **Invalid input is handled.** A malformed UUID gives 400 with the reason, an unknown one
  404, an over-long path 404. No 500s.
* **Foreign keys are complete.** 157, every one with an explicit `ON DELETE` (129 CASCADE, 28
  SET NULL). Every table has a primary key. No orphaned episodes or titles, no duplicate
  `(anime_id, number)` episode pairs.
* **No broken internal links**, and **no dead controls** — every button a static scan flagged
  turned out to be wired.

## CRITICAL

### YUME-AUDIT-0001 — The pre-namespace key migration needed room for the library twice · **fixed**

`apps/web/src/shared/state/store.js:120` · S

`ensureProfiles()` moved three pre-namespace localStorage keys to their `::<viewer-id>`
spelling by writing the new key and then deleting the old one, so for a moment the value
existed twice. The founder's library is the whole catalogue, which the store already knows
does not fit in the quota once — see the trimming in `saveEntries`. `localStorage.setItem`
threw `QuotaExceededError` out of the first statement of `App.init()`, the router never ran,
and `<main id="page">` stayed empty.

Every symptom pointed away from it: `/` returned 200 with the right HTML, every module
returned 200 with the right content type, `/v1/health` was fine, and the server log was clean.

**Fixed** by freeing the old value before writing the new one, and putting it back if the
write still fails. Reproduced before and after in headless Chromium against an image built
from this commit: 6 000 pre-namespace entries, blank page with 0 children before, rendering
after with all 6 000 carried across and one copy in storage.
`apps/web/test/store-migration.test.mjs` covers it against a fake `Storage` with a real quota,
and fails on the old code.

## HIGH

### YUME-AUDIT-0002 — 11 703 anime carried no `anilist_id`, so the enricher could never match them · **fixed**

`apps/api/src/integrations/anilist/sync.ts:468` · M

This superseded the hypothesis the audit was asked to check. The `anime_mappings_mal_id_key`
collision **was already fixed**: migration 0026 and `writeMalId()` replaced the raising
`UPDATE`, and 368 conflicts are on record where a run used to lose 9 650 rows.

What the live database said:

| | rows |
| --- | ---: |
| anime | 32 390 |
| **without a synopsis** | **13 038** |
| — of those, with an `anilist_id` | 1 335 |
| — of those, **without** an `anilist_id` | **11 703** |

`upsertMedia()` finds its row with `WHERE anilist_id = $1` and returns `false` when there is
none. Those 11 703 came from a MAL-keyed dump holding a `mal_id` only, so the enricher had
never been able to see them — 36% of the catalogue, and 90% of the missing descriptions.

**Fixed** with `linkAniListIdsFromMal()`: AniList answers `media(idMal_in: [...])`, so the id
we lack is looked up with the id we have, 50 at a time on the same paced connection, and the
basic pass runs it first so anything it attaches is enriched by the same run. Collisions go
through `writeAniListId()`, which is guarded the same way `writeMalId()` is and records the
pair rather than moving a mapping. Ids AniList does not know are recorded as `not_found`
instead of being retried for ever.

### YUME-AUDIT-0003 — The SPA fallback answered a missing client module with `index.html` and a 200 · **fixed**

`apps/api/src/app.ts:452` · S

`setNotFoundHandler` returned `index.html` for any non-API GET, which is right for
`#/anything` and wrong for `/src/pages/whatever.js`. A module that stopped resolving was
served as HTML with a 200; the browser refuses to execute it, the page went blank, and every
check an operator makes reported health. This is what made YUME-AUDIT-0001 take a day to find.

**Fixed**: a path inside the client's own asset tree is a file request, so a miss under
`/src`, `/css` or `/assets` is a 404 with a problem document. Verified in a browser —
`/src/app/nope.js` → `404 application/problem+json`; `/admin/audit` and
`/whatever/somebody/typed` still return the application. Three tests in
`static-exposure.test.ts` pin both halves.

### YUME-AUDIT-0004 — `POST /v1/anime/resolve` let any account create catalogue rows at the global rate · **fixed**

`apps/api/src/modules/catalogue/public-routes.ts:366` · S

The route creates an anime stub for any AniList id it has not seen, and carried only the
300-a-minute global limit. One ordinary account could insert hundreds of thousands of rows a
day into `anime` — the table this instance most needs to protect.

**Fixed**: `WRITE_LIMIT`, plus a per-account cap of 200 new titles a day
(`ANIME_STUB_DAILY_MAX`), plus an `anime.create` audit entry recording who added each one —
which is also what the cap counts, through the existing `(actor_id, created_at DESC)` index,
so there is no second ledger to keep in step. Verified: over the cap the route answers 429
with a sentence saying so, and an existing title still resolves normally.

### YUME-AUDIT-0005 — `docker build -t yume-test .` failed · **fixed**

`Dockerfile:15` · S

The restructure that created `infrastructure/` moved the Dockerfile and left nothing at the
root, so the habitual command exited with `open Dockerfile: no such file or directory`. CI
passed throughout, because the workflow named the file explicitly and so could not warn
anybody.

**Fixed** by moving it back to the repository root, where `docker build .` looks for it. The
build context had to be the root either way. `docker-compose.yml` (six services), the CI
workflow, the README and `paths.test.ts` all follow it. `docker build -t yume-test .` exits 0.

## MEDIUM

### YUME-AUDIT-0006 — Tokens lived in localStorage, where script could read them · **fixed**

`apps/api/src/modules/auth/routes.ts:96` · L

There was no cookie anywhere in the API, so `HttpOnly`, `Secure` and `SameSite` were not
merely unset — they were unavailable. Both tokens sat in localStorage, and the refresh token
is good for 30 days.

**Fixed**: the refresh token is now an `HttpOnly; Secure; SameSite=Strict` cookie scoped to
`/v1/auth`, and the client drops the field on the way in. Verified in a browser after signing
in through the client's own `login()`: `localStorage` holds `accessToken` and `expiresAt`
only, and the cookie comes back `httpOnly: true, sameSite: Strict, path: /v1/auth`.

Two deliberate limits, stated rather than glossed:

* **The access token stays in localStorage.** It is fifteen minutes long and `user()` is read
  synchronously to decide what to draw, so moving it out of reach would mean a signed-out
  flash on every reload. Fifteen minutes readable is a very different exposure from thirty
  days.
* **`HttpOnly` does not defeat XSS**, it defeats *exfiltration*. A script on the origin can
  still use the session while the page is open, because the browser attaches the cookie to
  the page's own fetches. What it can no longer do is copy the token out and keep the account
  for a month from somewhere else.

Rollable rather than a flag day: `/refresh` reads the cookie first and the body second, so a
client loaded before the change keeps working. Verified both ways, and that logout clears the
cookie and the revoked cookie then refuses.

`apps/web/src/shared/ui/charts.js:253` · S

### YUME-AUDIT-0008 — The metric-age probe scanned every `system_metrics` partition · **fixed**

`apps/api/src/modules/system/diagnostics.ts:268` · S

`SELECT max(created_at) FROM system_metrics` had no index it could use. Measured on the live
database: a parallel sequential scan over 231 944 rows, 2 689 buffers, 28 ms, on every
diagnostics run, with 34 198 such scans on record.

**Fixed**: 0039 indexes `created_at` on the partitioned parent, and the probe asks only about
the last seven days so the planner prunes. Measured on 200 000 seeded rows: index-only scans,
**8 buffers, 0.21 ms**. Seven days is far outside the 180-second staleness threshold, so no
verdict changes — only the wording, which now says "no sample in the last 7 days" rather than
"never".

### YUME-AUDIT-0009 — Withdrawn: the mapping-conflict review queue already exists · **wontfix**

`database/migrations/0026_mapping_conflicts.sql:24`

### YUME-AUDIT-0010 — 1 335 anime had an AniList id and still no synopsis · **fixed**

`apps/api/src/integrations/anilist/sync.ts:251` · M

Originally filed as *not checkable statically*, because `metadata_runs` records counts and not
per-row outcomes — so "AniList has no description", "the run has not reached it" and "an
operator locked the field" looked identical from outside.

**Fixed** by recording the thing that was being thrown away. `resolveFields` already decides,
per field, whether the incoming value was applied, refused, or absent upstream; migration 0040
adds `metadata_attempts` and the enricher writes that decision down — `updated`, `unchanged`,
`no_synopsis`, `not_found`, `locked` or `failed`, one row per title per source. A title with
no row has never been attempted, which is why absence is meaningful and nothing is pre-seeded.

The Metadata section shows the split, so the majority case — nothing to fetch, chasing it is
wasted effort — stops looking like a failure.

### YUME-AUDIT-0011 — User-facing write routes with only the global rate limit · **fixed**

`apps/api/src/modules/comments/routes.ts:146` · S

Eleven routes an ordinary account can reach carried only 300 requests a minute, which is a
flooding budget rather than a limit: comment likes, forum topic edits, library writes and
deletes, favourites, progress, profile, settings and both watch-together routes.

**Fixed**: `WRITE_LIMIT` on all eleven. Verified — `PATCH /v1/profiles/me` now answers with
`x-ratelimit-limit: 30`.

### YUME-AUDIT-0012 — 246 pairs share a title exactly, and the duplicate scan saw 48 of them · **fixed**

`apps/api/src/modules/catalogue/metadata-repository.ts:138` · M

The original finding — "222 canonical titles are held by more than one anime row" — was true
but the suggested fix was half wrong: a duplicate finder and a merge tool already existed.
What was actually wrong is sharper, and measurable:

| | pairs |
| --- | ---: |
| Share a canonical title exactly | 246 |
| Visible to the old scan | 48 |
| **Invisible** — different year or format | **185** |
| **Invisible** — no year on one side | **11** |

`findDuplicates` required the two rows to agree on `season_year` and `format`, which threw
away the strongest signal there is — and disagreeing about the year is one of the things a
duplicate pair does.

**Fixed** with an exact-title pass that does not require them, and it is the default. 246
pairs in 73 ms. Verified functionally as well: three rows differing in both year and format
are proposed by the exact pass and by neither the old one nor the similar pass.

Nothing merges anything automatically — an identical title two decades apart is usually a
remake — so the route stays read-only and an operator with `anime.merge` confirms each one.

### YUME-AUDIT-0013 — `/v1/admin/audit` was already taken · **fixed**

`apps/api/src/modules/analytics/routes.ts:232` · S

The audit-status report was specified at `GET /v1/admin/audit`, which is the audit log's
route. Fastify refuses a duplicate route **at startup**, so registering the second one would
have stopped the application booting. Resolved by giving the two audits distinct names: the
report is at `/v1/admin/audit/report` and section key `audit` (so `/admin/audit` names it),
and the log's section key moved to `audit-log`.

### YUME-AUDIT-0014 — The palette had no yellow, so two severities shared the amber hue · **fixed**

`apps/web/css/tokens.css:72` · S

**Fixed**: `--yellow-400/500` added, and the four severities are four hues. Measured in a
browser: `rgb(236,101,101)`, `rgb(248,195,89)`, `rgb(251,232,106)`, `rgb(128,128,128)`. They

### YUME-AUDIT-0023 — The similar-title duplicate scan takes 68 seconds · **open**

`apps/api/src/modules/catalogue/metadata-repository.ts:147` · M

Found while fixing 0012, and it is why nobody had worked through the duplicates: opening the
tab ran this. `similarity()` is a function call, so the trigram index cannot serve it and
every pair inside every `(year, format)` bucket is compared — **68 seconds** measured on the
live catalogue, against 73 ms for the exact pass.

**Mitigated, not solved.** The fast pass is the default and this one is a button an operator
presses, labelled as slow, so nothing is blocked. A LATERAL rewrite against the GIN index was
measured at **165 seconds** and is not the answer; a real fix needs a different bound — a
precomputed normalised-title key, or an offline pass writing candidates to a table.
